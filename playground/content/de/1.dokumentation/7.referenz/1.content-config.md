`content.config.ts` legt fest, welche Dateien zur Website gehören und welche öffentlichen Routen Ginko Content daraus ableitet. Ginko Docs exportiert eine Factory für das unterstützte Docs-Modell mit optionalem Blog.

```ts [content.config.ts]
import { defineGinkoDocsConfig } from "@lupinum/ginko-docs/content";

export default defineGinkoDocsConfig({
  site: {
    name: "Example Docs",
    description: "Dokumentation für Example.",
    url: "https://docs.example.com",
  },
  locales: ["en", "de"],
  defaultLocale: "en",
  blog: true,
});
```

## Factory-Optionen

```ts [Öffentlicher Typ]
interface GinkoDocsContentOptions {
  site: { name: string; description: string; url: string };
  locales?: Array<"en" | "de">;
  defaultLocale?: "en" | "de";
  blog?: boolean;
}
```

| Option             | Typ                   | Standard                                   | Wirkung                                                      |
| ------------------ | --------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| `site.name`        | `string`              | erforderlich                               | Seitentitel in Agent-Metadaten und generiertem Home-Eintrag  |
| `site.description` | `string`              | erforderlich                               | Beschreibung in Agent-Metadaten und generiertem Home-Eintrag |
| `site.url`         | `string`              | erforderlich                               | Absolute Origin für Agent-Links                              |
| `locales`          | `Array<'en' \| 'de'>` | `['en']`                                   | Von der Factory erzeugte Content-Sprachen                    |
| `defaultLocale`    | `'en' \| 'de'`        | Erster Eintrag in `locales`, danach `'en'` | Sprache des Home-Eintrags unter `/`                          |
| `blog`             | `boolean`             | `false`                                    | Ergänzt `blog` und `authors` und hält Blogrouten aktiv       |

Der Typ akzeptiert `defaultLocale: 'de'`, und die rohe Factory verwendet als Fallback die erste konfigurierte Sprache. Der aktuelle App-Shell- und Routenvertrag setzt jedoch Englisch als kanonische Standardsprache voraus. `en` ist deshalb heute der einzige dokumentierte und unterstützte Wert. Unterstützte Setups sind Englisch allein sowie zweisprachiges Englisch/Deutsch mit Englisch als Standard.

## Generierte Collections

Die Factory erstellt immer `docs`. Nur mit `blog: true` ergänzt sie `blog` und `authors`.

| Collection | Typ    | Quelle                   | Collection-Routenmount                             | Sitemap | Agent-Markdown     |
| ---------- | ------ | ------------------------ | -------------------------------------------------- | ------- | ------------------ |
| `docs`     | `page` | Abhängig vom Sprachmodus | `/docs` auf Englisch, `/dokumentation` auf Deutsch | Ja      | Bereich `optional` |
| `blog`     | `page` | `2.blog/**/*.md`         | `/blog`                                            | Ja      | Bereich `blog`     |
| `authors`  | `data` | `authors/**/*.json`      | Keine                                              | Nein    | Nein               |

Alle drei Collections verwenden `strict: true`. Ungültige Dokumente stoppen die Verarbeitung, statt nur eine Warnung auszugeben.

### Einsprachige Quellen

Im unterstützten englischen Einsprachenmodus verwendet die Factory diese Struktur:

```text [Einsprachiger Content]
content/
├── docs/**/*.md
├── 2.blog/**/*.md       # nur mit blog: true
└── authors/**/*.json    # nur mit blog: true
```

Docs liegen unter `/docs`, Blogbeiträge unter `/blog`. Collection-i18n bleibt ungesetzt. Als reine Implementierungswirkung würde eine einzelne deutsche Locale den Docs-Mount `/dokumentation` wählen; der vollständige Layer unterstützt diese Konfiguration derzeit nicht als dokumentiertes Setup.

### Zweisprachige Quellen

Mit mehr als einer Sprache aktiviert die Factory Collection-i18n und verwendet diese sprachrelativen Globs:

```text [Zweisprachiger Content]
content/
├── en/
│   ├── 1.docs/**/*.md
│   ├── 2.blog/**/*.md       # nur mit blog: true
│   └── authors/**/*.json    # nur mit blog: true
└── de/
    ├── 1.dokumentation/**/*.md
    ├── 2.blog/**/*.md       # nur mit blog: true
    └── authors/**/*.json    # nur mit blog: true
```

Das exakte Docs-Quellmuster lautet `{1.docs,1.dokumentation}/**/*.md`. Routen mounten unter `/docs` für `en` und `/dokumentation` für `de`. Die Blogroute lautet in beiden Sprachen `/blog`.

Mit der unterstützten englischen Standardsprache und der Nuxt-I18n-Strategie ergeben sich daraus die öffentlichen Docs-Roots `/docs` und `/de/dokumentation`.

## Generierte Agent-Konfiguration

Die Factory leitet die Agent-Site aus `site` ab, aktiviert Metadaten-Frontmatter und verwendet diese Felder in der angegebenen Reihenfolge:

```text [Agent-Metadatenfelder]
title, description, url, route, locale, section, collection, source, updated
```

Sie erstellt den Bereich `optional` mit dem Titel `Documentation` und der Reihenfolge `100`. Mit `blog: true` kommt der Bereich `blog` mit dem Titel `Blog` und der Reihenfolge `40` hinzu.

Für jede Sprache entsteht ein App-eigener Home-Eintrag. Die Standardsprache verwendet `/`, jede weitere Sprache `/<locale>`. Titel, Beschreibung, Metadaten und gerendertes Markdown stammen aus `site`.

## Collection-Invarianten

Das generierte Modell hält eine eindeutige Quelle der Wahrheit:

- `docs` und `blog` sind routenbasierte Page-Collections.
- `authors` enthält abfragbare Daten und erhält weder öffentliche Route noch Sitemap-Eintrag oder Agent-Seite.
- Docs- und Blogseiten aktivieren normalisiertes Raw-Markdown, `llms.txt` und `llms-full.txt`.
- Entwürfe sind in der Entwicklung sichtbar, fehlen aber in Produktions-Agent-Ausgabe und öffentlicher Navigation.
- Partials werden nicht zu öffentlichen Seiten.

Verwende `defineGinkoDocsConfig()` als vollständige Content-Konfiguration. Eine zusätzliche Neudeklaration derselben Collections erzeugt konkurrierende Schemas und Routenregeln.
