Ginko Docs renders ordinary Markdown with its prose components and exposes 34 authored tags for content that needs more structure. Use a tag when it makes a sequence, choice, warning, or relationship easier to scan.

## Add a structured component

Write capitalized component tags directly in Markdown. Quoted attributes become props; the Markdown between opening and closing tags fills the default slot. Ginko Content handles this syntax through Comark. Keep each opening tag on one line; the Markdown body can span any number of lines.

```mdc [content/docs/1.getting-started.md]
<Steps mode="numbered">
### Install the packages

Add Ginko Docs and Ginko Content to the Nuxt project.

### Extend the layer

Add `@lupinum/ginko-docs` to `nuxt.config.ts`.
</Steps>
```

Use components only when their structure helps the reader scan or act. Normal paragraphs and lists remain clearer for ordinary prose.

## Nest opening and closing tags

Each component closes with its own name, such as `</Tab>`. Nest children inside their parent without counting punctuation. Within `<Steps>`, level-three headings divide the prose into steps.

```mdc [content/docs/install.md]
<Tabs layout="line">
<Tab label="pnpm">
Install with pnpm.
</Tab>

<Tab label="npm">
Install with npm.
</Tab>
</Tabs>
```

Use self-closing tags for components without content, such as `<Figure src="/images/photo.webp" alt="A flower" />`. Keep opening and closing tags together when moving a block. Named slots use `<template #title>…</template>`. For numbers, booleans, lists, and objects, use literal JSON attributes such as `:zoom="false"`; a bare boolean attribute means `true`. These bindings accept data, not JavaScript expressions.

## Choose the tag for the job

| Need                                        | Start with                               |
| ------------------------------------------- | ---------------------------------------- |
| Ordered instructions                        | `steps` with level-three headings        |
| A warning or aside                          | GFM alerts, `note`, `warning`, or `info` |
| Switchable alternatives                     | `tabs` and `tab`                         |
| Linked choices                              | `cards` and `card`                       |
| A directory shape                           | `files` with a nested Markdown list      |
| An image with a caption or fixed dimensions | `figure`                                 |
| Adjacent API fields                         | `api` with static JSON props               |
| Dated changes                               | `timeline` and `timeline-item`           |

The [MDC component reference]($docs/components/mdc-components) puts every built-in component on one page, with live examples, copyable Markdown, properties, slots, and defaults. Author only static prop values; dynamic Vue bindings are rejected by the content policy.

## Edit components visually

Applications using Ginko Editor can import `ginkoDocsAuthoringKitSource` from `@lupinum/ginko-docs/authoring`. The source provides component policy, implementation metadata, insertion recipes, and editing instructions. Create the editor kit with `createAuthoringKit()` from `@lupinum/ginko-editor/authoring`.

The visual kit includes `info`, `note`, `warning`, `error`, `success`, `idea`, `aside`, `excerpt`, `layout`, `column`, `flow`, and `figure`. Edit a callout title or an aside label directly on the writing canvas. Open the block’s cog for its properties; callouts also let you change the callout type while keeping the title and body. Excerpts provide a source field there. For two columns, drag the divider between small/large, medium/medium, and large/small. You can also focus the divider and use the arrow keys. Each change updates both columns together. Existing layouts with other column counts remain intact.

Use `@lupinum/ginko-docs/component-kit` as a Nuxt module when an application needs these renderers without the documentation shell. The module registers the kit's components and scoped styles. The host supplies its icon component and keeps its own routes, fonts, and content setup.

The other Docs tags remain available in Markdown. They are not yet included in the visual kit. Tabs and accordions need controls for adding and ordering items. Cards need dedicated media controls. Figures already expose image source, alternative text, caption, and layout properties; a media picker can follow. Steps and timelines need controls for their repeated structure. Quizzes, API groups, read-more links, and file trees need structured data fields. Inline keys, centers, drop caps, code groups, collapsed content, and tables of contents also require their own editing behavior before they join the kit.

## Keep ordinary content ordinary

A component should express a real content relationship, not decorate a paragraph. Prefer headings, lists, tables, blockquotes, and code fences when standard Markdown already carries the meaning.

When the built-ins cannot represent a repeated product concept, follow the [custom component guide]($docs/customization/custom-components) to register the Vue component, authored tag, render policy, and optional agent serializer as one contract.
