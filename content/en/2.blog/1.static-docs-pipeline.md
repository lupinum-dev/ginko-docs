The Lupinum website treats content as source, not as a runtime service dependency. Docs pages and blog posts live in typed Ginko Content collections, and the app reads those collections directly.

## Why the hard cutover matters

The old CMS path and the new content path should not both own route data. A dual setup makes search, sitemap, and page metadata harder to reason about.

The migration keeps a single content contract:

- `content.config.ts` defines the collections.
- Markdown and YAML files hold source content.
- Route components query Ginko Content and render full documents through `<ContentRenderer>`.

## What changed in the app shell

Blog routes use `useContentMany()` for lists and `useContentPage()` for details. Page metadata comes from frontmatter so route components do not duplicate titles, descriptions, dates, or reading-time labels.

## Verification targets

The static build has to prove more than "the page renders." It must prerender routes, produce correct canonical tags, include docs and blog URLs in the sitemap, and pass browser checks without client console errors.
